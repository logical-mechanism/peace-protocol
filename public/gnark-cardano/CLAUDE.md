# gnark-cardano — Claude Instructions

This is a toolkit for getting gnark Groth16 proofs onto the Cardano blockchain using Aiken smart contracts. It handles the full pipeline from circuit definition to on-chain verification.

## Project Structure

```
proof.pattern    — User's proof specification (THE INPUT — read this first)
run              — Full pipeline script: build → prove → test
scripts/         — Individual pipeline steps
go/              — Go CLI: circuit compilation, proof generation, JSON export
  circuit.go     — GENERATED by Claude from proof.pattern (.gitignore'd)
  circuit_test.go— GENERATED by Claude (.gitignore'd)
  ceremony.go    — MPC ceremony commands (init/contribute/verify/finalize)
  main.go        — CLI dispatch: setup, prove, verify, re-export, ceremony
aiken/           — Aiken on-chain Groth16 verifier (types + pairing check)
  lib/gnark_cardano/groth.ak             — Generic verify_groth16 + verify_commitments
  lib/gnark_cardano/limb_compression.ak  — Re-compress 12-limb slices to G1 bytes
  lib/gnark_cardano/example.ak           — ExampleSpendRedeemer type (shared with tests)
  validators/example_spend.ak            — Worked Plutus V3 spend validator + tests
python/          — Python datum converters (gnark JSON → Cardano CLI format)
data/            — Generated: Cardano datum files for on-chain use
example/         — Worked pattern examples covering every input type combination
  *.pattern                              — Pattern files (one per shape)
  inputs/                                — Matching JSON inputs for `./snark prove -input`
CEREMONY.md      — Step-by-step guide for running an MPC trusted setup ceremony
```

## The Workflow

1. User writes `proof.pattern` describing what they want to prove
2. User prompts Claude: "Generate the circuit from proof.pattern"
3. Claude generates `go/circuit.go` + `go/circuit_test.go`
4. User runs `./run` (or the individual scripts below)

The `./run` script handles everything after circuit generation:
- `./scripts/build` — compile Go CLI + trusted setup
- `./scripts/prove` — generate proof, export JSON, convert to Cardano datums, generate circuit-specific Aiken test
- `./scripts/test` — run Aiken + Python tests

## Scripts

```bash
./scripts/check-deps    # verify go, aiken, python3, pytest are available
./scripts/build         # compile Go CLI + trusted setup → go/setup/
./scripts/prove         # prove + export + datums + generate aiken/lib/tests/circuit.ak
./scripts/test          # run aiken check + pytest
./scripts/lint          # go vet + aiken build + ruff
./run                   # all of the above in sequence
```

**Note:** `./scripts/build` always deletes and recreates `go/setup/` from
scratch. This is intentional — switching circuits (e.g. regenerating
`circuit.go` from a different `proof.pattern`) leaves stale setup files that
have the wrong number of public inputs, causing `prove` to fail with
"invalid witness size". Re-running `./run` always gets you a clean state.

## Claude's Job

After the user writes `proof.pattern`, Claude generates THREE files:

1. **`go/circuit.go`** — the gnark circuit + `CompileCircuit()`, `CircuitSetup()`, and `CircuitProve()` functions
2. **`go/circuit_test.go`** — Go-level round-trip test (**required**, see below)
3. **`example/inputs/<pattern-name>.json`** (if the pattern doesn't already have one in `example/inputs/`) — a working JSON input file matching the `circuitInputs` struct, with an `_comment` key documenting the shape. See [The `circuitInputs` JSON Convention](#the-circuitinputs-json-convention) below.

`CompileCircuit()` is required even though it's tiny — it's the entry point
used by both single-party setup (`CircuitSetup`) and the MPC ceremony code
(`ceremony.go`), so that ceremony.go doesn't need to know the concrete circuit
struct name. It must look exactly like:

```go
func CompileCircuit() (constraint.ConstraintSystem, error) {
	var circuit MyCircuit
	return frontend.Compile(ecc.BLS12_381.ScalarField(), r1cs.NewBuilder, &circuit)
}
```

Everything else (build, export, datum conversion, Aiken test generation) is handled by the scripts.

**These files are per-user generated artifacts** (`.gitignore`'d). Running "Generate the circuit from proof.pattern" will overwrite them.

### Pattern Mapping Comment (required)

Every generated `circuit.go` MUST include a comment block at the top of `Define()` that maps
each pattern line to the corresponding gnark code. This lets the user verify the circuit
faithfully represents their pattern without reading gnark internals.

Format:
```go
func (c *MyCircuit) Define(api frontend.API) error {
	// Pattern mapping:
	//   Secret Int Inputs: (x)       → c.X (frontend.Variable, secret)
	//   Public Int Inputs: (y)       → c.Y (frontend.Variable, public)
	//   Constants: d                 → const d = 42
	//   compute: result = x * x + d → xSquared := api.Mul(c.X, c.X); result := api.Add(xSquared, d)
	//   check: y == result           → api.AssertIsEqual(c.Y, result)
	...
}
```

### Negative Tests (required)

Every generated `circuit_test.go` MUST include negative test cases that verify the circuit
rejects invalid inputs. These catch bugs where the circuit compiles and runs but doesn't
actually enforce the pattern's constraints.

Rules for negative tests:
- **At least one negative test per `check:` line** — mutate one side of the equality
- **At least one negative test per `compute:` line** — provide inputs that don't satisfy the computation
- **Wrong public output** — correct secret, wrong public value
- **Wrong secret** — a secret that doesn't produce the claimed public output
- Use `assert.ProverFailed()` for all negative cases

Example for `check: y == x * x + d`:
```go
// Wrong y (off by 1)
assert.ProverFailed(&Circuit{}, &Circuit{X: 7, Y: 90}, test.WithCurves(ecc.BLS12_381))
// Wrong x for given y
assert.ProverFailed(&Circuit{}, &Circuit{X: 8, Y: 91}, test.WithCurves(ecc.BLS12_381))
```

## Reading proof.pattern

The proof.pattern file describes a zero-knowledge proof using this format:

```
Secret <Type> Inputs: (<name1>, <name2>, ...)    → circuit private witnesses
Public <Type> Inputs: (<name1>, <name2>, ...)    → circuit public witnesses
Constants:
    <name>  # description                        → hardcoded circuit values
compute: <name> = <expression>                    → in-circuit computation
check: <lhs> == <rhs>                            → equality assertion
```

**Types:** `Int` (Fr scalar), `G1` (BLS12-381 G1 point), `G2` (G2 point), `Fq12` (pairing result)

**Expressions:**
- `e(A, B)` → BLS12-381 pairing (A: G1, B: G2 → Fq12)
- `[scalar]point` → scalar multiplication
- `A + B` → point addition
- `H(x)` → hash function (always MiMC — see below)
- `q^a` → shorthand for `[a]q` (scalar mul of generator)
- `x * y` → field multiplication
- `x >= y` / `x <= y` → range comparison

**Comparisons:** `>=` and `<=` use `api.Cmp()` or bit decomposition. These are expensive in-circuit (many constraints) so use sparingly.

### Constants vs Public Inputs

These two pattern declarations look superficially similar but mean completely different things:

- **`Constants:`** are values **baked into the circuit at compile time**. They become part of the verifying key (via the constraint system) and cannot be changed without re-running trusted setup. Use this for things that genuinely never change: curve generators, fixed protocol parameters, domain-separation tags, a fixed G2 base point in a pairing.

- **`Public <Type> Inputs:`** are values **the verifier supplies at proof-check time**, typically from the on-chain context (a redeemer field, a datum, a constant in a Plutus validator). They appear in `public.json["inputs"]` and the on-chain verifier consumes them position-by-position with the IC entries.

Rule of thumb: **if it could conceivably differ across two valid proofs of the same circuit, it's a Public Input. Otherwise it's a Constant.** A G1 generator is always a Constant. A counterparty's public key is always a Public Input. A fixed G2 "domain" point used in a hashing scheme is a Constant. The user's BLS public key, looked up from a UTxO datum, is a Public Input.

Picking wrong has real costs:
- A G2 generator that should be a Constant but is declared as a Public Input adds **24 limbs** to every public-input vector and forces the on-chain verifier to do an extra G2 uncompression.
- A user-supplied G1 point that should be a Public Input but is hardcoded as a Constant means every user shares the same circuit and the proof is meaningless ("I proved a fact about a fixed point that I baked in at setup time").

## Compile Time and Constraint Counts

**Heads up: gnark circuits with G1 / G2 / pairing operations are large.** Plain Int arithmetic compiles in seconds; emulated curve arithmetic compiles in minutes for non-trivial cases. Some real numbers from this repo's example circuits:

| Pattern | Constraints | Compile + setup time (rough) |
|---|---|---|
| simple-preimage | ~few hundred | < 1 s |
| square-plus-constant | ~few hundred | < 1 s |
| range-proof | ~tens of thousands | a few seconds |
| schnorr-knowledge | ~80K | ~5 s |
| diffie-hellman | ~160K | ~10 s |
| peace-protocol | ~2M | ~1–2 min |
| bls-signature | ~1.7M | ~1 min |

**The single biggest cost driver is `pairing.Pair`.** Each invocation adds ~700K–900K constraints. A circuit with two pairings (e.g. `bls-signature`) is twice as expensive as one with a single pairing. Scalar multiplications (`ScalarMul`, `ScalarMulBase`) add ~80K constraints each. MiMC and Int arithmetic are essentially free in comparison.

**Implications for users writing patterns:**
- `./run` time is dominated by trusted setup, which scales linearly with constraint count. A 2M-constraint circuit takes ~1–2 minutes per `./run` invocation.
- Iteration loop: if you're tweaking a pattern that involves pairings, expect every cycle to take a minute. Use `go test -run TestX -v` for a faster feedback loop on circuit semantics — it skips trusted setup entirely.
- If your pattern can be rewritten to push a pairing **out of the circuit** (e.g. compute it off-chain and verify the result via a hash), do it. The on-chain verifier will check the underlying Groth16 proof regardless.

## Hashing: Always Use MiMC

**`H(x)` always means MiMC.** It's the only hash function that's both cheap in-circuit and native to gnark's BLS12-381 field. SHA256 works but costs ~25,000 constraints vs ~300 for MiMC.

When hashing different types, Claude handles the conversion automatically:

| Input to H() | What Claude generates |
|---|---|
| `H(int)` | Write the Fr element to MiMC, call `Sum()` |
| `H(int1, int2, ...)` | Write multiple Fr elements, call `Sum()` |
| `H(fq12_value)` | Decompose Fq12 to 12 Fp coefficients → reduce each to a native Fr element via limb arithmetic → write all 12 Fr values to MiMC → `Sum()`. This is the `Fq12ToFrElements` pattern — Claude generates the decomposition code automatically. |
| `H(g1_point)` | Reduce each Fp coordinate (X, Y) to a native Fr element via the limb-based `fpToNativeFr` helper → write the two Fr values to MiMC → `Sum()`. See [example/point-commitment.pattern](example/point-commitment.pattern) for the verified end-to-end pattern. |

**The user never needs to know about `Fq12ToFrElements` or type decomposition.** Just write `H(k)` and Claude handles it based on `k`'s type from the `compute:` line above.

### Hashing G1 Points: the `fpToNativeFr` Helper

`H(g1_point)` and `H(fq12_value)` both rely on the same trick: cheaply reducing an
emulated `Fp` element to a single native `Fr` `frontend.Variable`, suitable as a
direct MiMC input. The math is:

```
x_fp = Σ limb[i] * 2^(64*i)        (canonical limb representation)
x_fr = x_fp mod r
     = Σ limb[i] * (2^(64*i) mod r)  (everything taken mod r since native field IS Fr)
```

Claude generates this helper inline (do not factor it into `helpers.go`):

```go
// pow64[i] = 2^(64*i) mod r — precomputed at package init.
var pow64 = func() []*big.Int {
    const limbs = 6
    base := new(big.Int).Lsh(big.NewInt(1), 64)
    frMod := emparams.BLS12381Fr{}.Modulus()
    out := make([]*big.Int, limbs)
    out[0] = big.NewInt(1)
    for i := 1; i < limbs; i++ {
        out[i] = new(big.Int).Mul(out[i-1], base)
        out[i].Mod(out[i], frMod)
    }
    return out
}()

func fpToNativeFr(
    api frontend.API,
    fpField *emulated.Field[emparams.BLS12381Fp],
    x *emulated.Element[emparams.BLS12381Fp],
) frontend.Variable {
    // ReduceStrict ensures limbs are canonical (< p) before treating
    // them as little-endian limbs of a non-redundant representation.
    xr := fpField.ReduceStrict(x)
    var acc frontend.Variable = 0
    for i, limb := range xr.Limbs {
        acc = api.Add(acc, api.Mul(limb, pow64[i]))
    }
    return acc
}
```

Inside `Define()`:

```go
fpField, err := emulated.NewField[emparams.BLS12381Fp](api)
if err != nil { return err }

xFr := fpToNativeFr(api, fpField, &c.PX)
yFr := fpToNativeFr(api, fpField, &c.PY)

h, err := mimc.NewMiMC(api)
if err != nil { return err }
h.Write(xFr, yFr)
digest := h.Sum()
```

**The off-chain `CircuitProve` test mode and `circuit_test.go` MUST mirror this exactly,**
or the digest won't match and `verify` will fail. Use native MiMC plus
`bls12381_fr.Element.SetBigInt`, which auto-reduces mod r:

```go
var px, py big.Int
p.X.BigInt(&px)
p.Y.BigInt(&py)

// SetBigInt auto-reduces mod r, mirroring fpToNativeFr's algebraic reduction.
var xFr, yFr bls12381_fr.Element
xFr.SetBigInt(&px)
yFr.SetBigInt(&py)

h := nativemimc.NewMiMC()
h.Write(xFr.Marshal())
h.Write(yFr.Marshal())
digest := h.Sum(nil)

var result bls12381_fr.Element
result.SetBytes(digest)
```

**This pairing of in-circuit `fpToNativeFr` + native `SetBigInt` is a load-bearing
invariant.** If you change one side, you MUST change the other or proof generation
will silently produce a witness that fails verification. The test cases in
[example/point-commitment.pattern](example/point-commitment.pattern) exist precisely
to catch any future drift.

### Native MiMC in CircuitProve test mode

When `CircuitProve` needs to compute a MiMC hash for test inputs (e.g. `y = H(x)`), use the **native** gnark-crypto mimc package — not the in-circuit one. This requires an import alias since both packages are named `mimc`:

```go
import (
	nativemimc "github.com/consensys/gnark-crypto/ecc/bls12-381/fr/mimc"  // native (for CircuitProve test mode)
	"github.com/consensys/gnark/std/hash/mimc"                            // in-circuit (for Define())
)
```

The native hash pattern (used in both `CircuitProve` test mode and `circuit_test.go`):

```go
h := nativemimc.NewMiMC()
var elem bls12381_fr.Element
elem.SetBigInt(&x)
b := elem.Marshal()
h.Write(b)
digest := h.Sum(nil)
var result bls12381_fr.Element
result.SetBytes(digest)
result.BigInt(&y)
```

**There is no `ComputeMiMCHash` helper function.** Always inline this pattern.

## The `circuitInputs` JSON Convention

Every generated `circuit.go` defines a private `circuitInputs` struct used by the `-input <file.json>` mode of `./snark prove`. The struct shape varies per circuit (different patterns need different fields), but the field-naming convention is fixed so users have a predictable mental model.

**The convention** (Claude must follow this when generating `circuit.go`):

| Pattern declaration | Go struct field type | JSON value type |
|---|---|---|
| `Secret Int` | `string` (decimal) | decimal string |
| `Public Int` (user-supplied, e.g. range bound) | `string` (decimal) | decimal string |
| `Secret G1` | `string` (named `*Hex`) | 96-char hex |
| `Public G1` (user-supplied, e.g. counterparty key) | `string` (named `*Hex`) | 96-char hex |
| `Secret/Public G2` | `string` (named `*Hex`) | 192-char hex |

**Why decimal strings for ints:** BLS12-381's Fr is 254-bit. A native JSON number tops out at ~`2^53` and silently loses precision. JSON parsers across languages handle decimal strings consistently; numeric integers in JSON do not.

**What does NOT go in the JSON:**
- **Constants** — they're baked into the circuit and never user-supplied.
- **Public values derived from secrets** — e.g. for `H(x) == y`, the user supplies `x` and `CircuitProve` computes `y` itself. The JSON has `{"x": "..."}`, not `{"x": "...", "y": "..."}`.

**Where to find the exact shape for a given pattern:** read the `circuitInputs` struct near the top of the generated `circuit.go`. Each field has a JSON tag that maps to the JSON key name. The field name suffix (`Hex` for points, no suffix for ints) tells you the expected encoding.

**Ready-made input files** for every pattern in `example/` live in [example/inputs/](example/inputs/), one JSON file per pattern. They double as documentation: every file has an inline `_comment` key (JSON unmarshaling silently drops unknown keys) describing the pattern's shape and any gotchas.

When Claude generates a new `circuit.go`, it should also generate (or update) the matching `example/inputs/<pattern>.json` so the user has a working `-input` example out of the box.

## Generating circuit.go from proof.pattern

Map the pattern to gnark circuit code:

### Type Mapping

| Pattern Type | gnark Circuit Field | gnark Assign Type |
|---|---|---|
| `Secret Int` (used only in native arithmetic) | `A frontend.Variable` | `big.Int` |
| `Secret Int` (used as a scalar in G1/G2 ops) | `A emulated.Element[emparams.BLS12381Fr]` | `emulated.ValueOf[BLS12381Fr](&bigInt)` |
| `Public Int` | `Y frontend.Variable \`gnark:",public"\`` | `big.Int` |
| `Public G1` | split into `VX, VY emulated.Element[emparams.BLS12381Fp] \`gnark:"vx,public"\`` (see "G1 Public Inputs" below) | `emulated.ValueOf[BLS12381Fp](&coord)` |
| `Secret G1` | split into `PX, PY emulated.Element[emparams.BLS12381Fp]` (no tag → secret) (see "Secret G1/G2 Inputs" below) | `emulated.ValueOf[BLS12381Fp](&coord)` |
| `Public G2` | split into 4 fields `PkXA0, PkXA1, PkYA0, PkYA1 emulated.Element[emparams.BLS12381Fp] \`gnark:"pkxa0,public"\`` etc. (see "G2 Public Inputs" below) | `emulated.ValueOf[BLS12381Fp](&coord)` |
| `Secret G2` | same 4-field split as Public G2 but without the `,public` tag | `emulated.ValueOf[BLS12381Fp](&coord)` |

**Why Secret Int has two rows:** `frontend.Variable` lives in the native (Fr) field. `sw_emulated.Curve.ScalarMul` / `ScalarMulBase` require `*emulated.Element[ScalarField]`, so any secret scalar that feeds a G1 (or G2) operation MUST be declared as the emulated form. Mixing the two adds expensive bit-decomposition. For simple Int-only circuits (e.g. preimage hashing), stick with `frontend.Variable`.

**Why every G1/G2 row says "split":** Both G1 and G2 emulated structs have the visibility-tag-propagation issue (see the dedicated sections below). Splitting into named coordinate fields is the only verified-working approach for both public and secret variants. The split layout is also what makes pre-generation sizing predictable — see the [Pre-Generation Sizing](#pre-generation-sizing) table.

### Expression Mapping

| Pattern | gnark Code |
|---|---|
| `e(A, B)` | `pairing.Pair([]*sw_bls12381.G1Affine{&A}, []*sw_bls12381.G2Affine{&B})` |
| `[s]P` | `sw_bls12381.ScalarMulBase(api, s)` or `ScalarMul(api, P, s)` |
| `A + B` | `sw_bls12381.Add(api, A, B)` |
| `H(x)` | MiMC: `mimc.Write(x)` then `mimc.Sum()` — type-dependent decomposition as above |
| `x >= y` | `api.AssertIsLessOrEqual(y, x)` or bit decomposition |
| `check: a == b` | `api.AssertIsEqual(a, b)` or point equality assertion |

### G1 Public Inputs

In gnark v0.14, `sw_bls12381.G1Affine` is `sw_emulated.AffinePoint[BLS12381Fp]` — a struct
holding two `emulated.Element[BLS12381Fp]` coordinates. To expose a G1 point as a public
input, declare each coordinate as its own tagged field, then reconstruct the affine point
inside `Define()`:

```go
import (
    sw_emulated "github.com/consensys/gnark/std/algebra/emulated/sw_emulated"
    "github.com/consensys/gnark/std/math/emulated"
    "github.com/consensys/gnark/std/math/emulated/emparams"
)

type Circuit struct {
    VX emulated.Element[emparams.BLS12381Fp] `gnark:"vx,public"`
    VY emulated.Element[emparams.BLS12381Fp] `gnark:"vy,public"`
}

func (c *Circuit) Define(api frontend.API) error {
    curve, err := sw_emulated.New[emparams.BLS12381Fp, emparams.BLS12381Fr](
        api, sw_emulated.GetBLS12381Params())
    if err != nil { return err }

    v := sw_emulated.AffinePoint[emparams.BLS12381Fp]{X: c.VX, Y: c.VY}
    _ = curve.ScalarMul(&v, &someEmulatedScalar)
    // ...
}
```

Each `emulated.Element[BLS12381Fp]` flattens to **6 native (Fr) limbs** in the public
witness vector, so each public G1 contributes 12 entries (X then Y, 6 limbs each). This
is the verified pattern used by [app/snark/kappa.go](../../app/snark/kappa.go)'s
`vw0w1Circuit` and the diffie-hellman example. Witness assignments use
`emulated.ValueOf[emparams.BLS12381Fp](&bigIntCoord)`, where the coord comes from
`bls12381.G1Affine.X.BigInt(&bi)` / `.Y.BigInt(&bi)`.

**Do not** try to declare a single `V sw_bls12381.G1Affine \`gnark:",public"\`` field —
the visibility tag does not reliably propagate through the nested emulated struct, and
the resulting witness ordering is unverified. Always split into named X/Y coordinate
fields.

### G2 Public Inputs

A BLS12-381 G2 point lives in `Fp2 = Fp[u]/(u² + 1)`, so each coordinate has two `Fp`
components (`A0 + A1·u`). To expose a G2 point as a public input, declare **four**
`emulated.Element[emparams.BLS12381Fp]` fields — one per Fp2 component — then
reconstruct the affine point inside `Define()`:

```go
import (
    bls12381 "github.com/consensys/gnark-crypto/ecc/bls12-381"
    sw_bls12381 "github.com/consensys/gnark/std/algebra/emulated/sw_bls12381"
    "github.com/consensys/gnark/std/math/emulated"
    "github.com/consensys/gnark/std/math/emulated/emparams"
)

type Circuit struct {
    PkXA0 emulated.Element[emparams.BLS12381Fp] `gnark:"pkxa0,public"`
    PkXA1 emulated.Element[emparams.BLS12381Fp] `gnark:"pkxa1,public"`
    PkYA0 emulated.Element[emparams.BLS12381Fp] `gnark:"pkya0,public"`
    PkYA1 emulated.Element[emparams.BLS12381Fp] `gnark:"pkya1,public"`
}

func (c *Circuit) Define(api frontend.API) error {
    pairing, err := sw_bls12381.NewPairing(api)
    if err != nil { return err }

    // Reconstruct pk by direct field assignment. G2Affine.P is the
    // unexported g2AffP type, but its X, Y fields (typed as
    // fields_bls12381.E2) are exported, so direct assignment works —
    // gnark itself uses this pattern internally in Pairing.MuxG2.
    var pk sw_bls12381.G2Affine
    pk.P.X.A0 = c.PkXA0
    pk.P.X.A1 = c.PkXA1
    pk.P.Y.A0 = c.PkYA0
    pk.P.Y.A1 = c.PkYA1

    // Now usable in pairings:
    _, err = pairing.Pair([]*sw_bls12381.G1Affine{&someG1}, []*sw_bls12381.G2Affine{&pk})
    return err
}
```

Each of the four `emulated.Element[BLS12381Fp]` fields flattens to **6 native (Fr)
limbs** in the public witness vector, so each public G2 contributes **24 entries** to
`public.json["inputs"]`. Witness assignments populate them from a native `bls12381.G2Affine`:

```go
var pkxa0, pkxa1, pkya0, pkya1 big.Int
pkAff.X.A0.BigInt(&pkxa0)
pkAff.X.A1.BigInt(&pkxa1)
pkAff.Y.A0.BigInt(&pkya0)
pkAff.Y.A1.BigInt(&pkya1)

assignment := &Circuit{
    PkXA0: emulated.ValueOf[emparams.BLS12381Fp](&pkxa0),
    PkXA1: emulated.ValueOf[emparams.BLS12381Fp](&pkxa1),
    PkYA0: emulated.ValueOf[emparams.BLS12381Fp](&pkya0),
    PkYA1: emulated.ValueOf[emparams.BLS12381Fp](&pkya1),
}
```

This is the verified pattern used by [example/bls-signature.pattern](example/bls-signature.pattern).

**G2 generators and other fixed G2 constants:** when a G2 point is a *constant*
(known at circuit-compile time, e.g. the curve generator), do not declare it as an
input at all. Wrap a native `bls12381.G2Affine` with `sw_bls12381.NewG2AffineFixed`
inside `Define()` — this precomputes pairing lines and yields a much cheaper Miller
loop than a runtime-variable G2:

```go
_, _, _, g2Native := bls12381.Generators()
g2Fixed := sw_bls12381.NewG2AffineFixed(g2Native)
result, err := pairing.Pair([]*sw_bls12381.G1Affine{&sig}, []*sw_bls12381.G2Affine{&g2Fixed})
```

**Do not** declare a single `Pk sw_bls12381.G2Affine \`gnark:",public"\`` field — the
visibility tag does not propagate through the unexported `g2AffP` wrapper, and the
resulting witness ordering is unverified. The 4-field split is the only validated path.

### Secret G1/G2 Inputs

Secret point inputs use the **same coordinate splitting as their public counterparts**,
just with the `,public` tag removed (or omitted entirely — the gnark default is secret).
Splitting is still required: trusting visibility-tag propagation through the nested
emulated struct is unsafe even on the secret side, because the witness ordering is
undocumented and the reconstruction inside `Define()` would have to match it.

**Secret G1** (verified by [example/bls-signature.pattern](example/bls-signature.pattern)
and [example/point-commitment.pattern](example/point-commitment.pattern)):

```go
type Circuit struct {
    SigX emulated.Element[emparams.BLS12381Fp] `gnark:"sigx"`
    SigY emulated.Element[emparams.BLS12381Fp] `gnark:"sigy"`
}

func (c *Circuit) Define(api frontend.API) error {
    sig := sw_bls12381.G1Affine{X: c.SigX, Y: c.SigY}
    // ... use sig in pairings, scalar mul, etc.
}
```

**Secret G2** (analogous, untested but identical structurally to Public G2):

```go
type Circuit struct {
    PkXA0 emulated.Element[emparams.BLS12381Fp] `gnark:"pkxa0"`
    PkXA1 emulated.Element[emparams.BLS12381Fp] `gnark:"pkxa1"`
    PkYA0 emulated.Element[emparams.BLS12381Fp] `gnark:"pkya0"`
    PkYA1 emulated.Element[emparams.BLS12381Fp] `gnark:"pkya1"`
}
// Reconstruction inside Define() is identical to the Public G2 example above.
```

Secret coordinate fields do **not** appear in `public.json["inputs"]` and do **not**
contribute to `nRawPublic`. They still feed gnark's auto-commitment machinery, so a
circuit with any emulated point input — public or secret — produces a commitment-extension
proof (see Quirk #5).

### Scalar Test Edge Cases

gnark's emulated `ScalarMulBase` / `ScalarMul` use **incomplete addition formulas** that
fail with `NewHint: no modular inverse` when the algorithm internally hits a doubling
or point-at-infinity case. This shows up most often with degenerate scalars:

- **`sk = 1`** → `[1]g = g`, and the GLV decomposition inside `ScalarMulBase` ends up
  adding `g` to itself, tripping the formula. **Tests must use `sk ≥ 2`.**
- Other small powers of 2 and the curve's GLV lattice corners can also trip it; if a
  test fails with "no modular inverse", first try a non-power-of-2 scalar like 7, 11,
  or a 30-digit random integer before assuming a circuit bug.

This is a gnark library limitation, not a circuit bug — the on-chain verifier accepts
proofs over the full Fr range. The constraint only applies to in-circuit witness
generation during testing.

### Commitment Extension (Pedersen)

If any secret inputs should be committed (for CCA security), use gnark's commitment API:

```go
// In circuit struct
A frontend.Variable `gnark:"a,secret"`  // committed secret

// In compile options
ccs, err := frontend.Compile(ecc.BLS12_381.ScalarField(), r1cs.NewBuilder, &circuit,
    frontend.WithCommitment(commitment.Pedersen, "a"))
```

This adds commitment fields to the proof (D point + PoK) that the Aiken verifier checks.

### Pre-Generation Sizing

**Before writing `circuit.go`, compute the expected `nRawPublic` and `nCommitments` from the pattern.** Locking these down up front lets you sanity-check `vk.json` and `public.json` after running the pipeline, instead of debugging a mysterious Aiken failure later.

| Pattern declaration | Limbs in public witness |
|---|---|
| `Public Int` (declared as `frontend.Variable`) | 1 |
| `Public G1` (split into `VX, VY emulated.Element[BLS12381Fp]`) | 12 (6 per coordinate) |
| `Public G2` (split into 4 `emulated.Element[BLS12381Fp]` fields) | 24 |
| `Public Fq12` | 72 (12 fields × 6 limbs) |

Then:

- `nRawPublic = sum of public-field limb counts`
- `nCommitments = 1` if the circuit uses **any** `emulated.Element` (G1, G2, pairing — including secret ones), `0` otherwise. *This is the auto-commitment from gnark v0.14's emulated arithmetic — see Quirk #5 below.* If you explicitly call `frontend.WithCommitment`, add 1 more per explicit commitment.
- **Expected `vk.json`:** `nPublic = nRawPublic + 1` and `len(vkIC) = nRawPublic + 1 + nCommitments`
- **Expected `public.json`:** `len(inputs) = nRawPublic + 1` (the `+1` is the leading `"1"` wire), and `commitmentWire` is non-empty iff `nCommitments > 0`

**Worked sizing examples:**

| Pattern | Public layout | `nRawPublic` | `nCommitments` | `nPublic` | `len(vkIC)` |
|---|---|---|---|---|---|
| simple-preimage | 1× Public Int | 1 | 0 | 2 | 2 |
| diffie-hellman | 3× Public G1 | 36 | 1 (auto) | 37 | 38 |
| peace-protocol | 3× Public G1 | 36 | 1 (auto) | 37 | 38 |
| bls-signature | 1× Public G1 + 1× Public G2 | 12 + 24 = 36 | 1 (auto) | 37 | 38 |
| point-commitment | 1× Public Int | 1 | 1 (auto, from secret G1) | 2 | 3 |

Note how **point-commitment** has the same `nRawPublic` as **simple-preimage** (just one public Int) but `nCommitments = 1` because of the secret G1. This is the auto-commitment behavior from Quirk #5: any emulated point input — even a *secret* one — promotes the proof to commitment-extension format.

### Verification Checklist

**After generating `circuit.go` and `circuit_test.go`, do all of the following before declaring the circuit working.** Skipping any step risks shipping a circuit that compiles, passes Go tests, and silently fails on-chain.

1. **`go test -run TestYourCircuit -timeout 600s`** — catches Define() bugs, witness assignment shape mismatches, and most edge cases. Fast feedback loop.

2. **`./run`** — runs the **full** pipeline: build → trusted setup → prove → export → datum convert → Aiken test generation → Aiken check → Python tests. **You MUST run this, not just `go test`.** The Aiken on-chain verifier is a separate code path with its own assumptions; `go test` only validates the in-circuit constraints, never the wire format the contract sees.

3. **Open `go/out/public.json` and verify:**
   - `len(inputs)` matches your pre-generation prediction
   - `inputs[0] == "1"` (the normalized contract — see Quirk #6)
   - `commitmentWire` is present iff you predicted `nCommitments > 0`

4. **Open `go/out/vk.json` and verify:**
   - `nPublic` matches `nRawPublic + 1`
   - `len(vkIC)` matches `nPublic + nCommitments`
   - `commitmentKeys` is non-empty iff `nCommitments > 0`

5. **Confirm `tests/circuit` passes in the Aiken output:**
   - `circuit_proof_valid` ✓
   - `circuit_commitments_valid` ✓ (only meaningful if `nCommitments > 0`)
   - `circuit_redeemer_valid` ✓

### Aiken Failure Triage

If `circuit_proof_valid` or `circuit_redeemer_valid` fails, **diagnose in this order before suspecting the Go circuit**:

1. **Length mismatch** — the most common silent failure. Compute:
   - `expected_public = vk.nPublic - 1`
   - `actual_public = len(public_values)` in the generated `aiken/lib/tests/circuit.ak`

   If they differ, the prove script's stripping logic is wrong for your circuit shape, or `orchestrate.go`'s normalization didn't fire. The Aiken loop pairs IC entries with public values position-by-position — even a one-off shifts every term and every test fails identically with no useful diagnostic.

2. **Auto-commitment surprise** — if `vk.json` shows `commitmentKeys` non-empty but you didn't expect it, you're hitting Quirk #5. Update your sizing predictions and re-verify the lengths in step 1.

3. **Then** suspect the circuit. Re-read `Define()`, check the pattern mapping comment, and verify your test assignments match the pattern's compute and check lines.

The first two should be ruled out before touching `circuit.go`, because the failure mode looks identical in all cases (a generic pairing mismatch with no diagnostic).

## Aiken Test Generation

The `./scripts/prove` script automatically generates `aiken/lib/tests/circuit.ak` from the proof artifacts. Claude does NOT need to generate this file.

The existing `aiken/lib/tests/groth.ak` contains known-good hardcoded tests that validate the generic verifier. The generated `circuit.ak` tests the specific circuit you built.

**If you need to understand the test format** (e.g., for debugging), here's the mapping:
- `out/vk.json` hex strings → Aiken `#"..."` byte literals (direct copy)
- `out/public.json` `inputs` → public values list, **with the leading `"1"` stripped**. `public.json["inputs"][0]` is always `"1"` post-normalization (see Quirk #6 below); the prove script and `gnark_public_to_aiken` both drop it before passing to `verify_groth16`.
- `out/public.json` `commitmentWire` → commitment wire integer (omitted when no Pedersen commitments)
- `nPublic` in vk.json follows the Aiken convention: includes the implicit "1" wire, so `nPublic = len(IC) - nCommitments`

## Aiken Verifier Details

The generic verifier in `aiken/lib/gnark_cardano/groth.ak` performs:

**Main Groth16 check:**
```
e(A, B) * e(vk_x, -gamma) * e(C, -delta) == e(alpha, beta)
```
where `vk_x = IC[0] + sum(IC[i+1] * pub[i]) + sum(IC[nPublic+j] * wire[j]) + sum(D[k])`

**Commitment PoK check:**
```
e(D_sum, gSigmaNeg) * e(PoK, g) == 1
```

Both use Cardano's built-in BLS12-381 primitives (no stdlib imports needed beyond `aiken/builtin`).

## Example Spending Validator

For users who want to actually deploy this on Cardano (not just verify proofs in tests), there's a worked example at [aiken/validators/example_spend.ak](aiken/validators/example_spend.ak). It's a Plutus V3 spending validator that:

1. **Loads the verifying key from the spent UTxO's datum** (`Option<SnarkVerificationKey>`).
2. **Reads the proof + raw G1 points from the redeemer** (`ExampleSpendRedeemer`, defined in [aiken/lib/gnark_cardano/example.ak](aiken/lib/gnark_cardano/example.ak)).
3. **Binds the raw G1 points to the proof's public-input limbs** using `gnark_cardano/limb_compression.verify_g1_list_against_compressed`. This is the critical step: it prevents a malicious prover from sending a valid-but-unrelated proof and claiming it's "about" different points.
4. **Calls `groth.verify_groth16`** to run the pairing check.

The validator targets the **diffie-hellman** circuit shape (3 public G1 points). Adapting it to a different pattern means changing:
- The redeemer fields (`pk`, `them`, `shared` → whatever your circuit's public points are called)
- The list passed to `verify_g1_list_against_compressed`
- Nothing else — the proof verification call stays identical

Frozen test data (VK + proof + commitment wire + the 36-limb public-input list) lives at the bottom of the same file in three tests: one positive, two negative (swapped points, tampered proof). This catches limb-binding bugs before they hit testnet.

### Limb Compression Library

The bridge between "raw G1 points the contract knows about" and "the integer limbs the proof committed to" lives at [aiken/lib/gnark_cardano/limb_compression.ak](aiken/lib/gnark_cardano/limb_compression.ak):

- `g1_compress_from_xy_limbs` — reassemble 12 little-endian u64 limbs into a 48-byte IETF-compressed G1 point. This is the inverse of what gnark does when it flattens an `emulated.Element[BLS12381Fp]` into the public witness.
- `verify_g1_limbs_against_compressed` — one-shot check: do the next 12 limbs match an expected compressed point?
- `verify_g1_list_against_compressed` — same thing for an ordered list of N points consuming 12*N limbs.

**Why compress on-chain instead of decompress?** Decompressing requires Fp arithmetic (modular square root) which is prohibitively expensive in Plutus. Compressing is just bit twiddling — pack the limbs back into bytes, set the compression and sign flags, done. The validator already has the trusted compressed bytes from the redeemer, so it just needs to verify "did the prover commit to these exact bytes?"

**G2 limb compression is not provided** — gnark's Fp2 ordering and G2 IETF flags add complexity, and the right abstraction depends on what your circuit does. For G2 public inputs (e.g. a BLS public key in [example/bls-signature.pattern](example/bls-signature.pattern)), the typical approach is to derive the limbs off-chain and trust them via a separate signature/datum check rather than reconstruct the compressed form on-chain. If you need on-chain G2 limb-binding for your specific use case, the structure mirrors the G1 helper — 4 Fp coordinates × 6 limbs = 24 limbs per G2 — but you'll need to adapt the IETF compression flags.

## MPC Trusted Setup Ceremony

For production deployments, the single-party `./snark setup` is insecure
because one machine knows the toxic waste. The toolkit also supports a
multi-party ceremony via the `snark ceremony` subcommand:

```bash
./snark ceremony init       -dir ceremony
./snark ceremony contribute -dir ceremony -phase 1   # each contributor
./snark ceremony verify     -dir ceremony -phase 1   # anyone can verify
./snark ceremony finalize   -dir ceremony -phase 1 -beacon <hex>
# repeat for phase 2
./snark ceremony finalize   -dir ceremony -phase 2 -beacon <hex> -out setup
```

The ceremony output format is **identical** to single-party setup output
(`ccs.bin`/`pk.bin`/`vk.bin` in `setup/`), so `./scripts/prove` and
`./snark prove` work unchanged with either. The ceremony is **purely
additive** — nothing forces users to run it for development.

Implementation lives in [go/ceremony.go](go/ceremony.go) and uses gnark's
built-in `backend/groth16/bls12-381/mpcsetup` package (Phase 1 = Powers of
Tau, Phase 2 = circuit-specific). Full user-facing guide is in
[CEREMONY.md](CEREMONY.md).

The ceremony code calls `CompileCircuit()` (defined in the generated
`circuit.go`) — that's why every generated `circuit.go` MUST export this
function, even though `CircuitSetup()` is the only other caller.

## Important gnark Quirks

1. **Implicit "1" wire:** gnark's public witness includes witness[0]=1 implicitly. The export code handles this via `ChoosePublicInputs()`. The Aiken verifier multiplies IC[0] by 1 (identity).

2. **Commitment wire:** When using Pedersen commitments, gnark computes `hash_to_field(D.Marshal() || committed_publics.Marshal())` as an additional public input. This must be passed separately to the Aiken verifier. When there are no commitments, the commitment wire and commitment fields are omitted entirely.

3. **IC length and nPublic convention:** `len(vk.IC) = nPublic + nCommitments`. `nPublic` includes the implicit "1" wire (IC[0]). The Aiken verifier computes `n_raw_public = nPublic - 1` to get the count of actual public inputs, then processes remaining IC entries with commitment wires. This means circuits with 0 commitments must still set `nPublic = len(IC)` (not `len(IC) - 1`).

4. **Point compression:** All G1 points are 48-byte IETF compressed (96 hex chars). All G2 points are 96-byte IETF compressed (192 hex chars). gnark-crypto's `.Bytes()` method produces this format.

5. **Auto-commitments from emulated arithmetic:** Circuits using `emulated.Element[BLS12381Fp/Fr]` (any G1/G2/pairing op) cause gnark v0.14 to automatically add **a Pedersen commitment wire** to the verifying key, even if the circuit never calls `frontend.WithCommitment`. The emulated package uses commitments internally to verify hint correctness. Symptoms:

   - `vk.json` contains a `commitmentKeys` entry you didn't ask for
   - `proof.json` contains `commitments` and `commitmentPok` fields
   - `public.json` contains a non-empty `commitmentWire` value
   - `len(vk.IC) = nRawPublic + 1 + 1` instead of `nRawPublic + 1`

   This is **expected and correct** — the toolkit's Aiken verifier and Python converters all handle the commitment-extension format. But it means you cannot assume "no `WithCommitment` call → no commitment". Any circuit with a public/secret G1 point will produce a commitment-extension proof.

6. **`public.json["inputs"]` always starts with `"1"` (post-fix).** Historically, [`ChoosePublicInputs`](go/export.go) had two branches that produced different output formats:

   - **Case 1 (no commitments):** returned `pubRaw` as-is, **no leading `"1"`**
   - **Case 2 (with commitments):** prepended `"1"`

   This inconsistency caused silent on-chain verification failures: the Python converter assumed leading `"1"` always present (broken for case 1), and the Aiken-test generator in `scripts/prove` assumed it was never present (broken for case 2). Both bugs canceled out for their respective common cases until the diffie-hellman example exposed it.

   **Current contract** ([go/orchestrate.go](go/orchestrate.go) normalizes after `ChoosePublicInputs`): `public.json["inputs"][0] == "1"` always. Both downstream consumers (`gnark_public_to_aiken` and the prove script's inline Python) drop `inputs[0]` before passing to the Aiken verifier, which independently uses `IC[0]` as the constant term.

   **If you write new code that reads `public.json["inputs"]`**, drop the leading `"1"` before pairing entries with `IC[1..]`.

7. **Aiken `verify_groth16` public-input format.** The Aiken verifier in [aiken/lib/gnark_cardano/groth.ak](aiken/lib/gnark_cardano/groth.ak) expects `public_values: List<Int>` to have length **`nPublic - 1`** — i.e. the actual public inputs *without* the implicit `"1"` wire. The constant term is handled internally by initializing the accumulator with `bls12_381_g1_uncompress(IC[0])`. Mismatched length silently shifts every IC index by one and the pairing check fails with no diagnostic. When debugging on-chain failures, **always count the entries first**: `len(public_values) == vk.nPublic - 1` and `len(commitment_wires) == nCommitments`.
