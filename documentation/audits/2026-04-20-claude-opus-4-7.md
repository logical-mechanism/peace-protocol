## Executive Summary

This is an incremental audit covering the nine commits on `app/contracts/` since the 2026-02-09 baseline. Two of those commits carry real logic changes:

- **4cc5b9d (2026-03-04)** — bidder time-lock (`locked_until` field, `minimum_bid_lock = 6h`) added to `BidDatum` and enforced on `EntryBidMint` + `RemoveBid`.
- **5e98ee4 (2026-03-25)** — `new_price: Int` field added to both `BidDatum` and `EncryptionDatum`, with new redeemers `UpdateBidPrice` and `UpdateEncryptionPrice`.

All other post-audit commits were formatting, copyright, CI, or release-prep churn. The cryptographic library code (`lib/types/{groth,schnorr,level,register}.ak`, `lib/limb_compression.ak`, `lib/digest.ak`) is unchanged at the instruction level since the prior audit and has been re-verified via direct inspection.

The protocol remains sound under the same assumptions documented in the prior crypto analysis (ECDLP, CDH, bilinear Diffie-Hellman, KEA, Blake2b-224 collision resistance, MiMC circuit security). The two new logic changes introduce no cryptographic regressions. They do, however, add a small set of new spend paths (`UpdateBidPrice`, `UpdateEncryptionPrice`) that inherit the same "owner may drain their own lovelace" pattern already present on the owner-signed encryption paths. These are low concern because an owner drains only their own deposit.

All prior HIGH findings remain intentional hyperstructure/penalty mechanisms per the original developer response. **MEDIUM-2 (Groth16 public-input length check) is still open and should still be addressed** — the developer was interested in a fix during the prior audit.

The new time-lock partially mitigates the `OBS-1` griefing vector noted previously, but does not fully close it (see [Focus section: Bidder time-lock](#focus-bidder-time-lock)).

**Status:** Carried from prior audit — code unchanged.

### MEDIUM-2: Groth16 Public Input Length Not Explicitly Validated

**Status:** **STILL OPEN.** Code unchanged since prior audit.
**Location:** [lib/types/groth.ak:78-116](../lib/types/groth.ak#L78-L116) (`derive_vk_x_combined`), called from [lib/types/groth.ak:159-207](../lib/types/groth.ak#L159-L207) (`verify_groth16`).

`derive_vk_x_combined` still uses `vk.nPublic - 1` to decide how many IC elements pair with the `public` list, then switches to the `wires` list. If `public` is shorter than expected, the function fails with `"public shorter than vkIC"`. If `public` is **longer**, the extra elements are silently ignored because the recursion terminates when `ic_tail` runs out.

The developer was interested in a fix during the prior audit but it was not implemented. A minimal fix is a length check before calling the helper:

```aiken
// In verify_groth16, after `let n_raw_public = vk.nPublic - 1`:
expect n_raw_public == list.length(public)
```

This assumes importing `aiken/collection/list` — but per the Groth optimization history the list stdlib carries a size cost. An alternative, stdlib-free check: after the recursion, require `public` to be fully consumed by returning a `(G1Element, List<Int>)` from `derive_vk_x_combined` and pattern-matching on `[]` for the remainder. Either approach would make silent over-provision impossible.

**Impact:** Not directly exploitable today — the VK is immutable in the reference datum, and providing the wrong public inputs makes the pairing fail regardless. However, any future change that makes `public` user-influenced (e.g., batched verification, multi-proof extensions) would be silently under-constrained. Tightening this now is a defence-in-depth fix.

### LOW-3: UpdateBidPrice / UpdateEncryptionPrice Allow Owner Self-Drain of Lovelace — NEW

**Location:** [validators/bidding.ak:196-228](../validators/bidding.ak#L196-L228) (`UpdateBidPrice`), [validators/encryption.ak:338-373](../validators/encryption.ak#L338-L373) (`UpdateEncryptionPrice`).

**Description:** Both update-price paths enforce that non-ADA tokens are preserved on the continuing output via `assets.without_lovelace(input.value) == assets.without_lovelace(output.value)`, but neither checks lovelace. Combined with the required owner signature, the practical effect is: the owner may update their price while simultaneously decreasing the lovelace balance of the continuing UTxO (down to ledger-level minUTxO).

**Impact:** Since only the owner signs, the only funds at risk are the owner's own. This is the same "owner drains own lovelace" pattern already present on the owner-signed branches of `UseSnark`, `UseEncryption`, and `CancelEncryption` (tracked under HIGH-3 in the prior audit). Not a griefing vector against third parties.

**Mitigating factors:**
- `extra_signatories` includes `owner_vkh` is a required check on both paths.
- Non-ADA tokens (the protocol NFT included) are preserved via `without_lovelace` equality.

**Recommendation:** If this pattern was accepted under HIGH-3 as a "penalty beam" for the owner, no action is required. If the intent is that `Update*Price` should only change the `new_price` field and preserve ADA, add:
```aiken
assets.lovelace_of(input.output.value) <= assets.lovelace_of(output.value),
```

**Developer response:** _pending_ — recommend acknowledging as carrying the same policy as HIGH-3.

## Focus Sections for Changed Code

### Focus: Bidder time-lock

**Commit:** 4cc5b9d (2026-03-04)

**Mechanism:**
- [lib/types/bidding.ak:11](../lib/types/bidding.ak#L11): `pub const minimum_bid_lock: Int = 1000 * 60 * 60 * 6` (6 hours, matching `pending_ttl`).
- [lib/types/bidding.ak:18](../lib/types/bidding.ak#L18): `locked_until: Int` added to `BidDatum`.
- [validators/bidding.ak:62-66](../validators/bidding.ak#L62-L66): at mint, `locked_until >= ub + minimum_bid_lock` is required.
- [validators/bidding.ak:126-139](../validators/bidding.ak#L126-L139): at `RemoveBid`, the lower bound of the validity range must satisfy `lb > locked_until`.

**Analysis — correctness:**
- Entry: requires `locked_until ≥ ub + 6h`. The bidder cannot claim a lock shorter than 6h post-entry.
- Removal: requires `lb > locked_until` strictly. This forces the removal transaction's lower bound beyond the lock. Standard Cardano pattern.
- `UseBid` (the cooperative path) intentionally does not check `locked_until` — the lock is designed to prevent unilateral pull, not to delay Alice's acceptance.

**Analysis — security vs. OBS-1 (prior audit griefing vector):**
Before the lock, Bob could `RemoveBid` immediately after Alice submits `UseSnark`, forcing Alice to `CancelEncryption` and eat a second transaction fee. The lock narrows the window: Bob can still `RemoveBid`, but only once his own stated `locked_until` is strictly in the past. If Bob bid at time T and Alice submits `UseSnark` at time T+Δ (Δ small), Alice's pending `ttl ≥ (T+Δ) + 6h` while Bob's lock expires at `locked_until ≥ T + 6h`. There remains a window of size Δ during which Bob could remove his bid while Alice is still pending. The lock therefore **reduces but does not eliminate** OBS-1. Alice remains protected by her ability to self-cancel with her signature regardless of TTL; the cost of griefing is still one additional transaction fee.

**Potential improvements (optional, not exploits):**
- **No upper bound on `locked_until` at entry.** A bidder may self-lock for any duration, including extreme values (e.g., `i64::MAX`). This is self-griefing (only hurts the bidder) and doesn't enable any attack, but a sane upper bound (e.g., `locked_until <= ub + 30d`) would reduce operator mistakes.
- **No explicit bound via `validity_range.upper_bound`.** The lock is compared only to `ub`. If the tx constructor sets an infinite upper bound, the constraint is unsatisfiable (`Finite` is required), so this is already safe.

**Tests:** No new tests were added for the time-lock (86 total, unchanged from prior audit). Adding tests for `locked_until` equality, boundary conditions, and the `RemoveBid` strict-inequality is recommended — see [Test Coverage Assessment](#test-coverage-assessment).

### Focus: Price in datum

**Commit:** 5e98ee4 (2026-03-25)

**Mechanism:**
- [lib/types/bidding.ak:19](../lib/types/bidding.ak#L19), [lib/types/encryption.ak:37](../lib/types/encryption.ak#L37): `new_price: Int` added to both datum types.
- [lib/types/bidding.ak:30](../lib/types/bidding.ak#L30): new `UpdateBidPrice(Int)` redeemer.
- [lib/types/encryption.ak:52](../lib/types/encryption.ak#L52): new `UpdateEncryptionPrice(Int)` redeemer.
- [validators/bidding.ak:196-228](../validators/bidding.ak#L196-L228) and [validators/encryption.ak:338-373](../validators/encryption.ak#L338-L373): `Update*Price` validators.
- [validators/encryption.ak:162,192,219](../validators/encryption.ak#L219): `UseEncryption` now binds `bid_new_price == next_new_price`.

**Analysis — what's enforced on-chain:**
1. `price >= 0` at both update paths.
2. Only the `new_price` field may differ between input and output datums; all other fields are preserved via `BidDatum { ..this_datum, new_price: price }` spread.
3. Non-ADA tokens (the NFT) are preserved on the continuing output.
4. `UpdateEncryptionPrice` is gated by `expect Open = status` — cannot update while Pending.
5. During `UseEncryption`, the new encryption datum's `new_price` must exactly equal the bid's `new_price`, binding the declared forward-looking price of the buyer into the resulting encryption state.

**Analysis — what's NOT enforced on-chain:**
1. **`new_price` is advisory, not a payment constraint.** The lovelace value of the bid UTxO is not checked against `new_price`. A bidder can declare `new_price = 1000_000_000` (1000 ADA) while placing only minUTxO in the bid UTxO. Alice, on accepting, receives only the actual lovelace.
   - **Likely intent:** `new_price` is the declared *resale* price the bidder would charge as the next seller, not what they're paying now. Under this reading, the payment amount is the bid UTxO's lovelace and `new_price` is simply information for future bidders.
   - **Off-chain obligation:** UIs must clearly distinguish "bid amount" (lovelace) from "declared resale price" (`new_price`). If any off-chain tool treats `new_price` as the bid amount, users could be misled.
2. **`UpdateBidPrice` is not gated by `locked_until`.** A bidder can change `new_price` at will during the lock window. This is fine if `new_price` is advisory; worth flagging if the product intent was "price is frozen once committed".
3. **`UpdateBidPrice` is not gated by anything other than owner signature + datum invariants.** There is no state check (no equivalent of `expect Open = status`) — a bid can have its price updated any number of times until `UseBid` or `RemoveBid`.

**Race conditions:** Between Alice's `UseSnark` (Tx1) and `UseEncryption` (Tx2), Bob could submit an `UpdateBidPrice` lowering `new_price`. The committed SNARK (Tx1) was computed with an older `new_price`, but **the SNARK does not include `new_price` as a public input** — only Bob's public key via `v`. So the SNARK remains valid. The `UseEncryption` check `bid_new_price == next_new_price` only binds Tx2's bid to Tx2's encryption output; it doesn't guarantee Alice saw any specific price when she constructed Tx1. This is an acceptable market behavior (Alice can refuse to submit Tx2 if she doesn't like the new declared price, since she signs Tx2), but UIs should surface `new_price` changes in the mempool if they are security-relevant to users.

### Focus: validators/reference.ak

**First-time coverage.** File: [validators/reference.ak](../validators/reference.ak) (15 lines, 159 compiled bytes).

```aiken
validator contract(_genesis_pid: PolicyId, _genesis_tkn: AssetName) {
  else(_) {
    fail @"I always fail :/"
  }
}
```

**Analysis:**
- No handlers for `mint`, `spend`, `withdraw`, `publish`, or `vote` — all paths hit the catch-all `else(_) { fail }`.
- Parameters `_genesis_pid` and `_genesis_tkn` are unused (`_`-prefixed). They exist so the compiled script hash varies with the genesis parameters, matching the parameterized pattern used by the other validators.
- The validator is **always-fail**, not always-true. Any transaction attempting to spend, mint from, withdraw against, publish under, or vote on this script fails.

**Security implications:**
- The reference datum UTxO — the protocol's configuration — sits at this address. Since all spend attempts fail unconditionally, the reference datum is **effectively immutable**: once created by the genesis mint, it cannot be moved, modified, or stolen.
- ADA or tokens accidentally sent to this address are permanently unspendable (locked forever). This is the stated hyperstructure philosophy.
- No cryptographic or authorization bypass is possible because no code path succeeds.

**Documentation discrepancy (DOC-1 in the INFO section below):** The root-level [SECURITY.md:38](../../../SECURITY.md#L38) describes this contract as "intentionally minimal, always-true by design." The code is **always-false** (`fail`). This should be corrected in SECURITY.md. The on-chain behavior is correct; only the prose is wrong.

## Additional Observations (Info)

### INFO-1: `new_price` is advisory, not payment-enforcing

See the [price-in-datum focus section](#focus-price-in-datum). The on-chain `new_price` field is a declarative value, not enforced against the bid UTxO's lovelace. Off-chain UIs carry the semantic responsibility of presenting "actual bid amount" (lovelace) separately from "declared future price" (`new_price`).

### INFO-2: Bidder may self-lock for arbitrary duration

[validators/bidding.ak:64](../validators/bidding.ak#L64) imposes only a lower bound on `locked_until`. A bidder can set a very large `locked_until` (e.g., years in the future) and be unable to `RemoveBid` until then. Only self-harm; no third-party attack surface. Consider an upper bound for UX robustness, not security.

### INFO-3: Bid time-lock partially mitigates OBS-1

See the [time-lock focus section](#focus-bidder-time-lock). The 6-hour minimum lock narrows but does not eliminate the OBS-1 griefing vector where Bob removes his bid during Alice's Pending window. Alice retains self-cancel capability in all cases.

### INFO-4: SECURITY.md mis-describes reference.ak (DOC bug)

[SECURITY.md:38](../../../SECURITY.md#L38) says: _"The reference contract (intentionally minimal, always-true by design)"_. The actual contract is always-**fail** (see [reference.ak focus section](#focus-validatorsreferenceak)). This is a documentation-only issue; the on-chain behavior is correct. Suggested fix: change "always-true" to "always-fail" in SECURITY.md.
