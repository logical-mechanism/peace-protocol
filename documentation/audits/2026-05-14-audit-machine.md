**Top three concerns**

1. **I-03** — `ReferenceDatum.snark_vk` and three of four script-hash fields are operator-trusted at bootstrap; the on-chain genesis check only pins `reference == reference_hash`. A mis-deployed `snark_vk` silently breaks every Groth verification semantic without breaking any validator. Documented as a Design Tradeoff; promote to spec.
2. **I-02** — There are zero validator-level negative tests. The H-01 perimeter fix is regression-tested at the `util.is_protocol_output` helper layer, but every validator inlines the same checks rather than calling the helper. A regression at any one of 11 inlined sites would not be caught by the existing suite.
3. **I-04** — The Schnorr knowledge proof (`schnorr.verify`) used in `EntryBidMint` and `EntryEncryptionMint` is bound only to `(generator, g^r, owner_g1.public_value)` and a domain tag; it is not bound to `owner_vkh` or any UTxO context. An attacker can replay a captured proof to mint bids/encryptions claiming someone else's G1 identity under their own vkh. The protocol intent (loose vkh↔g1 coupling vs. enforced binding) is undocumented; impact is bounded to bid-space spam and seller-cooperative griefing.

**Production / experimental assessment**: **Mainnet-ready** for a hyperstructure protocol after the v0.6.0 audit fixes, *subject to* (a) committing the bootstrap trust model to spec (I-03), (b) adding validator-level negative tests (I-02), and (c) making a deliberate decision on the Schnorr binding gap (I-04). This report finds no Critical, High, Medium, or Low security defects; all five new findings are Informational and four of them are documentation/coverage rather than code-level defects.

The report is readable for a non-auditor: every finding includes "What It Is" in plain English, the exact code excerpt, and the EUTxO semantic that makes it relevant.

## 3. Contract Overview

The PEACE protocol implements **proxy re-encryption** on Cardano. The data owner uploads ciphertext into a capsule held inside an encryption UTxO. A bidder places a bid (with locked lovelace) offering to buy the data. The current owner (seller) accepts a bid by re-encrypting to the bidder, the bid's NFT is burned, the bid's lovelace flows to the seller, and the bidder becomes the new owner. The whole flow is gated by a Groth16 SNARK verifying the re-encryption is correct and the Wang re-encryption math is well-formed.

**Protocol flow narrative**

1. **Genesis (one-shot, operator-driven).** The operator publishes a tx that spends a chosen `(tx_id, tx_idx)` UTxO and produces an output at the reference script address with the protocol's `ReferenceDatum` inline. The genesis mint policy fires, asserting that the parameterised UTxO is spent, that the output's `ReferenceDatum.reference` field equals the compile-time `reference_hash` parameter (M-01), and that the output has no attached `reference_script` and stake_credential = None.
2. **Encryption mint.** The data owner picks any UTxO they control as a seed; `EntryEncryptionMint` derives a token name from that UTxO's `OutputReference` (`bytes([idx]) + tx_id` truncated to 32 bytes — I-08 byte-for-byte off-chain parity). The mint validator requires: a Schnorr proof for `owner_g1`, a binding proof bound to `(token_name, half_level)`, `owner_vkh` to sign, a single-token-strict mint, and a continuing output to the encryption script with `stake_credential = None`, `reference_script = None`.
3. **Bidding.** Bidders mint bid NFTs via `EntryBidMint`, locking lovelace and committing to a 6-hour minimum-lock window. Bids reference an existing encryption (via a reference input) and Schnorr-prove `owner_g1`.
4. **Acceptance (two-step).** Seller calls `UseSnark` (signs, supplies a Groth proof via the `groth.withdraw` script in the same tx) to transition Open→Pending, storing the proof in the datum. Then the seller calls `UseEncryption` (signs again, references the chosen bid via `selected_bid_token`) — the bid's UseBid burns the bid token, the bid's lovelace flows to the seller, and the encryption datum advances to Open with the new owner.
5. **Cancellation / removal.** Pending can be cancelled by the owner or, after `ttl`, by anyone (the lovelace becomes drainable — H-04 carried Design Tradeoff). RemoveBid lets the bidder recover after `locked_until`. RemoveEncryption burns the encryption NFT (owner-signed).

**Major assets / tokens**

- **genesis NFT** `(genesis_pid, genesis_tkn)` — one-shot, lives on the reference UTxO. Authenticates the ReferenceDatum.
- **encryption NFTs** `(encryption_pid, fresh_tkn)` — one per encryption, fresh token name derived from a seed UTxO.
- **bid NFTs** `(bidding_pid, fresh_tkn)` — one per bid, fresh token name derived from a seed UTxO.

**Expected transaction shapes**

- **Genesis tx**: spends `(tx_id, tx_idx)`; mints `(genesis_pid, genesis_tkn, 1)`; produces one output at reference script address with `ReferenceDatum{reference, encryption, bid, groth, snark_vk}` inline + the genesis NFT.
- **EntryEncryptionMint tx**: spends a seed UTxO; mints `(encryption_pid, derived_tkn, 1)`; produces a continuing encryption output with `EncryptionDatum{owner_vkh, owner_g1, token, half_level, full_level: None, capsule, status: Open, new_price}`; references the genesis UTxO; owner_vkh signs.
- **UseSnark tx**: spends an Open encryption UTxO; runs `groth.withdraw` with `(proof, wire, public, ttl)`; outputs Pending(proof, public, ttl); owner_vkh signs; bounded validity range (1h max width).
- **UseEncryption + UseBid tx**: spends a Pending encryption UTxO + the chosen bid UTxO; burns the bid token; produces a new Open encryption output (new owner) and (implicitly) the seller's payment from the bid's lovelace; references the genesis UTxO; owner_vkh signs.
- **CancelEncryption tx**: spends a Pending encryption UTxO; rolls back to Open; either owner_vkh signs or `lb > ttl`.

**User roles**

- **Data owner** (seller): the current encryption UTxO's `owner_vkh`. Drives UseSnark and UseEncryption.
- **Bidder**: any wallet. Mints a bid, locks lovelace for ≥6h, can RemoveBid after lock.

**Admin roles**: none after genesis. The operator role is one-shot at deployment time only.

**Hyperstructure assumptions**: After the genesis mint, the protocol has no privileged signer, no admin, no upgrade path. Every protocol UTxO is NFT-authenticated; corrupted UTxOs (wrong datum shape, no NFT) are sweepable via the H-02/H-03 carried Intentional escape branches.

### 3.8 Builder-Bypass Question

**Is the validator safe if a malicious user bypasses any official off-chain builder?** **Yes — for every finding in this report.** No off-chain transaction builder exists in TARGET_CONTRACT_FOLDER, so the question reduces to "is the validator safe against any handcrafted Cardano transaction?". Every continuing-output / input-filter / NFT-strictness / signer-verification check is enforced on-chain. The H-01 perimeter pin is inlined at every site. The Groth proof is verified by the on-chain `groth.withdraw` script. The bid↔encryption coupling is bidirectional and enforced. The one residual off-chain trust point is the operator's choice of `ReferenceDatum.snark_vk` at bootstrap (I-03) — a handcrafted tx by a non-operator cannot tamper with this because the genesis policy is one-shot, but a malicious operator could deploy a backdoored vk.

**What It Is:**

The test suite covers helpers thoroughly: `util.is_protocol_output` is exercised against the four `stake_credential` variants and an attached `reference_script`; `search.for_*` helpers are exercised against extra-token / mismatched-token / empty-list cases; `schnorr.verify` and `binding_verify` are exercised positively and negatively; `verify_groth16` has happy and `fail_*` negative tests; `register.is_register_valid` has multiple invalid variants. Aiken validators run on a `Transaction` view. ### [I-03] Off-chain-only enforcement of `ReferenceDatum` content in genesis bootstrap

**Severity:** Informational

**Confidence:** Likely

**Status:** Design Tradeoff

**CWC ID:** CWC-005

**Root Cause:** `bootstrap-vk-trust`

**Component:** genesis bootstrap

**Location:**

- [validators/genesis.ak:30-55](../../contracts/peace-protocol/validators/genesis.ak#L30-L55)
- [lib/types/reference.ak:8-14](../../contracts/peace-protocol/lib/types/reference.ak#L8-L14)
- [compile.sh:24-71](../../contracts/peace-protocol/compile.sh)

**Quoted Code ([validators/genesis.ak:30-55](../../contracts/peace-protocol/validators/genesis.ak#L30-L55)):**

```aiken
expect Some(Output {
  address: output_address,
  datum: InlineDatum(output_datum_data),
  reference_script,
  ..
}): Option<Output> =
  search.for_output_by_token(outputs, policy_id, token_name)
expect ReferenceDatum { reference, .. }: ReferenceDatum = output_datum_data
let reference_datum_address: Address = address.from_script(reference)
and {
  assets.has_nft_strict(mint, policy_id, token_name),
  // M-01: pin the operator-supplied reference hash to the parameter
  // baked in at compile time. Without this check the reference field
  // would be operator-trust only, which would let a mis-deployed system
  // anchor protocol trust on a script the operator controls instead of
  // the always-fail reference.ak.
  reference == reference_hash,
  output_address == reference_datum_address,
  reference_script == None,
}
```

**What It Is:**

The genesis mint validator extracts only the `reference` field from the produced `ReferenceDatum`, asserts `reference == reference_hash` (the compile-time parameter — M-01), and asserts the output address matches `address.from_script(reference)`. The OTHER fields of the same `ReferenceDatum` — `encryption`, `bid`, `groth`, and most critically `snark_vk: SnarkVerificationKey` — are read from the operator's transaction but **never verified against any committed value**. Whatever the operator publishes for those fields becomes the protocol's authoritative source from then on.

If the operator deploys with `snark_vk = malicious_vk_that_always_verifies`, every `verify_groth16` call across the protocol's lifetime returns `True` for any proof shape that the malicious vk can accept. Every encryption re-encryption transition (`UseSnark` → `UseEncryption`) is then unconstrained: the seller can rotate ownership to any G1 point with a trivially-forged proof. Similarly, if `encryption`, `bid`, or `groth` script-hashes don't match the deployed validators, cross-validator coupling silently fails (no transactions ever validate), but a *partial* mismatch — e.g., correct `encryption` but malicious `groth` — would let the attacker substitute a Groth verifier that accepts anything.

**Why It Is Bad — Cardano Semantic Cited:**

Cardano validators don't run on UTxO creation (only on spend). The genesis mint policy DOES run at genesis-output creation, but it only checks what its body says to check. The four other ReferenceDatum fields are entirely operator-trusted at the moment of deployment, and the on-chain protocol has no way to discover later that the vk was wrong — every subsequent transaction validates against the wrong vk and the contradiction is invisible. This is the standard config-UTxO trust pattern (see `attacks/state.md` and `ctf/bank_05_misconfiguration.md`), constrained to a one-shot deployment.

**Attack Scenario:**

Malicious operator (or compromised deployment pipeline):

1. Operator chooses a SnarkVerificationKey for which they know the trapdoor (Groth16 is structured-reference-string based; whoever ran the trusted-setup knows the toxic waste).
2. Operator deploys the protocol normally: spends `(tx_id, tx_idx)`, mints `(genesis_pid, genesis_tkn, 1)`, produces a reference output with `ReferenceDatum{reference: correct_hash, encryption: correct, bid: correct, groth: correct, snark_vk: malicious_vk}`.
3. Users mint encryptions, place bids, accept bids — every Groth proof validates because the malicious vk accepts trapdoor proofs.
4. Operator (or anyone with the trapdoor) can rotate ownership of any encryption UTxO to themselves via a forged UseSnark + UseEncryption flow without paying a bid (they construct a Pending(forged_proof) and then any matching UseEncryption succeeds).

**Proof / Evidence:**

- Quoted code (above) — only `reference == reference_hash` is checked; the other fields are not.
- Cross-reference: [attacks/state.md](../../attacks/state.md) §5 "Misconfigured config UTxO as trust anchor", [ctf/bank_05_misconfiguration.md](../../ctf/bank_05_misconfiguration.md).
- Phase 1.6 trust table documents the operator as a one-shot anchor.

**How To Fix:**

Two complementary approaches:

1. **Promote the trust model to spec.** Document explicitly that:
   - `ReferenceDatum.snark_vk` is operator-chosen at bootstrap and trusted thereafter.
   - The operator's vk MUST come from a verifiable trusted-setup ceremony with public transcript.
   - The script hashes (`encryption`, `bid`, `groth`) MUST equal the hashes published in `hashes/*.hash` at deploy time and observers should verify them post-deployment.
2. **Optional belt-and-suspenders**: bake a `snark_vk_hash` constant into the genesis policy parameters (similar to `reference_hash`) and assert `blake2b_256(serialise_data(snark_vk)) == snark_vk_hash`. This lifts vk-trust from "operator-published once" to "compile-time-committed". Drawback: requires re-compiling the contract to upgrade the vk (which is the point — currently you can't upgrade the vk anyway because the reference UTxO is always-fail).

**Tests To Add:**

- Negative (validator-level — see I-02)
  - [ ] `test fail__genesis_mint_rejects_wrong_reference_hash` (M-01 regression — already implied)
  - [ ] If fix path 2 is taken: `test fail__genesis_mint_rejects_wrong_snark_vk_hash`
- Documentation
  - [ ] Update [README.md](../../contracts/peace-protocol/README.md) §Trust Model with the explicit bootstrap-trust statement

**Additional Notes:**

This is a **Design Tradeoff** under Phase 1.6 tiering rules: the trust model is partially documented (compile.sh + README + the M-01 audit-fix comment), so the finding is tiered as Informational rather than at the default CWC-005 severity (Critical). Promoting it to a written spec moves the documentation from `partial` to `documented`. Without promotion, a future auditor not paying close attention could miss that `snark_vk` is unverified.

The on-chain `reference == reference_hash` check (M-01) closes the most severe case (operator substituting their own script as the reference). The residual trust on the other ReferenceDatum fields is a smaller, more bounded surface — but it's still a place where the protocol cannot detect operator misbehaviour post-deployment.

**Knowledge References:**

- [attacks/state.md](../../attacks/state.md) §5 "Misconfigured config UTxO as trust anchor"
- [ctf/bank_05_misconfiguration.md](../../ctf/bank_05_misconfiguration.md)

- [taxonomy.md](../../taxonomy.md) — CWC-005 "Missing UTxO Authentication"

### [I-04] Schnorr knowledge proof does not bind `owner_vkh` or UTxO context

**Severity:** Informational

**Confidence:** Likely

**Status:** Open

**CWC ID:** CWC-033

**Root Cause:** `schnorr-vkh-binding-gap`

**Component:** `schnorr.verify` + EntryBidMint / EntryEncryptionMint

**Location:**

- [lib/types/schnorr.ak:30-67](../../contracts/peace-protocol/lib/types/schnorr.ak#L30-L67)
- [validators/bidding.ak:78-83](../../contracts/peace-protocol/validators/bidding.ak#L78-L83)
- [validators/encryption.ak:73-78](../../contracts/peace-protocol/validators/encryption.ak#L73-L78)

**Quoted Code ([lib/types/schnorr.ak:30-44](../../contracts/peace-protocol/lib/types/schnorr.ak#L30-L44)):**

```aiken
pub fn fiat_shamir_heuristic(
  // compressed g element
  g_b: ByteArray,
  // compressed g^r element
  g_r_b: ByteArray,
  // compressed g^x element
  u_b: ByteArray,
) -> ByteArray {
  // concat g_b, g_r_b, u_b, and b together then hash the result
  schnorr_domain_tag
    |> bytearray.concat(g_b)
    |> bytearray.concat(g_r_b)
    |> bytearray.concat(u_b)
    |> digest.hash
}
```

**What It Is:**

`schnorr.verify(owner_g1, schnorr_proof)` proves the prover knows the discrete log of `owner_g1.public_value` (under the canonical generator). The Fiat-Shamir preimage is `domain_tag ‖ g_b ‖ g_r_b ‖ u_b` — domain-separated but bound only to the public statement (the G1 point itself). The proof does NOT include:

- `owner_vkh` (the Cardano signing key the same datum requires)
- token_name / UTxO reference / mint policy
- expiry / nonce

So a valid Schnorr proof for `owner_g1 = u` is reusable across an unlimited number of mints, against any `owner_vkh`, for any token_name, with no time bound.

**Why It Is Bad — Cardano Semantic Cited:**

The protocol treats the *identity of a participant* as the pair `(owner_vkh, owner_g1)` — `owner_vkh` is the Cardano signing key (proves "I can sign this tx") and `owner_g1` is the BLS G1 public key (proves "I can do BLS-side cryptographic operations on this UTxO"). The Schnorr proof is what binds `owner_g1` to a real, well-formed point with a known discrete log. But because the Schnorr FS preimage doesn't include `owner_vkh`, the protocol does not enforce that the two are derived from the same principal.

The replay attack:

1. Alice publishes a valid Schnorr proof for `owner_g1 = u_alice` by minting a bid or encryption.
2. Attacker observes the proof on-chain.
3. Attacker mints a NEW bid with `BidDatum { owner_vkh: attacker_vkh, owner_g1: u_alice, ... }` and reuses Alice's Schnorr proof verbatim. The mint succeeds: `has(extra_signatories, attacker_vkh)` (attacker signs), `schnorr.verify(u_alice, alices_proof)` passes (replay), `register.is_register_valid(u_alice)` passes.
4. The bid now claims Alice's G1 identity but is owned (signing-key-wise) by the attacker.

**Attack Scenario:**

The downstream impact is bounded:

- **Best case for attacker**: spam the bid space with impersonation bids. Annoyance only — no value lost, no protocol invariant broken. Attacker spends their own lovelace to lock into the bid.
- **Worst case for the protocol**: a seller selects the impersonation bid for UseEncryption. The re-encryption succeeds (the BLS math doesn't care about `owner_vkh`), and the new encryption UTxO has `owner_vkh = attacker_vkh, owner_g1 = u_alice`. This UTxO is **unusable**:
  - `RemoveEncryption` requires `attacker_vkh` signature → attacker can drain the encryption's min-ADA.
  - `UseSnark` / `UseEncryption` (subsequent re-encryption) requires `attacker_vkh` signature AND a Groth proof that requires Alice's BLS secret to construct (via `verify_r5`'s `e(u, h0)` term that needs `x` such that `u = g^x`). Attacker can sign but can't construct the proof; Alice can construct the proof but can't sign.
  - Net effect: the encryption data is forever stuck. Alice's encrypted content is undecryptable to anyone who didn't already have access; Alice has no remedy on-chain.

The attacker's economic cost is the bid amount they locked. The protocol's loss is one DoS'd encryption per successfully accepted impersonation bid. The attack requires the seller to be careless (they could verify the bid's vkh matches the expected bidder's vkh off-chain), so it's seller-cooperative griefing rather than a unilateral attack.

**Proof / Evidence:**

- Quoted code (above) — FS preimage does not include `owner_vkh`.
- Cross-reference: [attacks/replay.md](../../attacks/replay.md) — payload-binding rules, CWC-033.
- Note: the *binding proof* in EntryEncryptionMint ([validators/encryption.ak:83-89](../../contracts/peace-protocol/validators/encryption.ak#L83-L89)) DOES bind to `token_name`, so the encryption-mint flow is partially protected. But the *Schnorr proof itself* (Phase 1 of identity verification) is reusable.

**How To Fix:**

Bind `owner_vkh` into the FS preimage of both `schnorr.verify` and `schnorr.binding_verify`. Suggested replacement for `fiat_shamir_heuristic`:

```aiken
pub fn fiat_shamir_heuristic(
  g_b: ByteArray,
  g_r_b: ByteArray,
  u_b: ByteArray,
  owner_vkh: VerificationKeyHash,
) -> ByteArray {
  schnorr_domain_tag
    |> bytearray.concat(g_b)
    |> bytearray.concat(g_r_b)
    |> bytearray.concat(u_b)
    |> bytearray.concat(owner_vkh)
    |> digest.hash
}
```

Then update `schnorr.verify` and the two call sites (EntryBidMint, EntryEncryptionMint) to thread `owner_vkh` through. Alternatively, if the intent is that `owner_vkh` and `owner_g1` SHOULD be allowed to differ (e.g., delegated bidders), document that intent in README + module-level doc string and leave the binding loose. Decide and document the trust model before changing the proof.

**Tests To Add:**

- Negative
  - [ ] `test fail__schnorr_verify_rejects_replay_with_different_vkh()` — exercises the post-fix binding
  - [ ] `test fail__bidding_mint_EntryBidMint_rejects_replayed_schnorr_proof_under_different_vkh()` (validator-level — see I-02)
  - [ ] same for encryption
- Documentation
  - [ ] Update [README.md](../../contracts/peace-protocol/README.md) to commit to the `(owner_vkh, owner_g1)` coupling decision

**Additional Notes:**

Severity tier rationale: per [audit.prompt.improved](../../audit.prompt.improved) Phase 5g, the default for CWC-033 is "High when the proof authorises spending value, Medium for participation proofs". The Schnorr proof here is a participation proof (knowledge-of-G1-secret) — the *spending* authorisation comes from `owner_vkh` + `extra_signatories`, not from the Schnorr proof. So the default would be Medium. Applying the value-leak-vs-principal-theft discipline: the attack does not enable principal theft (attacker pays the bid; attacker can't unlock anything they don't already own). The attack enables seller-cooperative griefing where a careless seller can be tricked into DoS'ing one encryption per attempt. That's borderline Low / Informational. The protocol's intent on `(vkh, g1)` coupling is undocumented, so this is recorded as Informational with a Documentation Backlog entry instructing the implementer to commit to a binding policy.

(borderline Low / Informational — picked Informational because the attack vector is seller-cooperative and the impact is one DoS'd UTxO per attempt at attacker-borne cost)

Not an attack — a measurement-integrity concern. The refactor ships. On mainnet, the genesis tx exceeds the budget. The bootstrap fails. The team discovers the bench was a stand-in.

- Comment in [lib/benchmarks/groth.ak:45-46](../../contracts/peace-protocol/lib/benchmarks/groth.ak#L45-L46) explicitly acknowledges the stand-in: "The bench is duplicated under the high-n name so the I-03 checklist row is satisfied; once a larger fixture exists the bench can be re-pointed at it."

### [O-01] `search.for_*` are O(N) linear scans; UseEncryption performs 4-5 such scans

**Severity:** Optimization

**Confidence:** Likely

**Status:** Optimization Opportunity

**CWC ID:** CWC-016

**Root Cause:** `linear-scan-no-indexer`

**Component:** `lib/search.ak` callers in encryption / bidding

**Location:**

- [lib/search.ak:32-135](../../contracts/peace-protocol/lib/search.ak#L32-L135)
- [validators/encryption.ak:125-303](../../contracts/peace-protocol/validators/encryption.ak#L125-L303)
- [validators/bidding.ak:115-215](../../contracts/peace-protocol/validators/bidding.ak#L115-L215)

**Quoted Code ([lib/search.ak:32-46](../../contracts/peace-protocol/lib/search.ak#L32-L46)):**

```aiken
pub fn for_output_by_token(
  outputs: List<Output>,
  pid: PolicyId,
  tkn: AssetName,
) -> Option<Output> {
  when outputs is {
    [] -> None
    [output, ..rest] ->
      if assets.has_nft_strict(output.value, pid, tkn) {
        Some(output)
      } else {
        for_output_by_token(rest, pid, tkn)
      }
  }
}
```

**What It Is:**

`search.for_output_by_token`, `for_input_by_token`, and `for_reference_datum` each scan their input list linearly until they find a match. Per redeemer, several such scans are performed:

- **encryption.UseEncryption** runs: `transaction.find_input(utxo)` (O(N) over inputs), `search.for_output_by_token` (O(N) over outputs), `search.for_reference_datum` → `for_input_by_token` (O(N) over reference inputs), `search.for_input_by_token` (O(N) over inputs again), `search.for_spend_redeemer_by_output_reference` (O(N) over redeemers). Five linear scans, three of which traverse the same list (inputs).
- **bidding.UseBid** runs: `transaction.find_input` (implicit, via `this_input`), `search.for_reference_datum` (O(N)), two `list.filter` over inputs (O(N) each), `search.for_spend_redeemer_by_output_reference` (O(N) over redeemers).

For a tx with K total inputs, the total work scales as O(K · #scans) = O(K · 5) ≈ O(5K) for UseEncryption. The `utxo_indexer` pattern (see [patterns/utxo_indexer.md](../../patterns/utxo_indexer.md)) would let the redeemer supply pre-computed indices into the inputs/outputs/reference_inputs lists, reducing each lookup to O(1) at the cost of small redeemer overhead.

**Why It Is Bad — Cardano Semantic Cited:**

Plutus V3 per-script budgets are tight. Linear scans over `tx.inputs` and `tx.outputs` are CPU-bounded by the actual transaction shape — a transaction with many wallet/change inputs (common for real wallets) pays for every step of every scan. The protocol cannot constrain N (anyone can include extra reference inputs / wallet inputs that don't affect validation but inflate scan cost). The `utxo_indexer` pattern is the canonical Aiken fix for this category of "validator must locate one specific thing in a list" cost.

**Attack Scenario:**

Not a security vulnerability. Cost concern: a future wallet that produces transactions with many native-asset-rich change inputs could push UseEncryption near or past the Plutus budget. The protocol stops being usable from that wallet until either the wallet changes its tx-shape strategy or the protocol adopts redeemer-supplied indices.

**Proof / Evidence:**

- Quoted code (above) — linear `when self is { [] -> ...; [x, ..rest] -> ... }` pattern.
- Cross-reference: [optimizations/aiken_optimization_guide.md](../../optimizations/aiken_optimization_guide.md) Pattern #12 (Avoid re-traversals), Pattern #20 (Don't compute, verify).
- [patterns/utxo_indexer.md](../../patterns/utxo_indexer.md) — canonical fix.

**How To Fix:**

Adopt the utxo_indexer pattern for high-fan-in redeemers. Add index fields to the redeemers:

```aiken
pub type EncryptionSpendRedeemer {
  RemoveEncryption
  UseEncryption(
    witness: ByteArray,
    r5: ByteArray,
    selected_bid_token: AssetName,
    binding_proof: BindingProof,
    // NEW: indices into the tx's input/output/ref_input/redeemer lists
    own_input_idx: Int,
    own_output_idx: Int,
    bid_input_idx: Int,
    bid_spend_redeemer_idx: Int,
    ref_input_idx: Int,
  )
  UseSnark(
    own_input_idx: Int,
    own_output_idx: Int,
    withdraw_redeemer_idx: Int,
    ref_input_idx: Int,
  )
  CancelEncryption(own_input_idx: Int, own_output_idx: Int)
  UpdateEncryptionPrice(price: Int, own_input_idx: Int, own_output_idx: Int)
}
```

Then replace each `search.for_*` call with an indexed access (`builtin.head_list`, `at`, or recursion-by-index) and assert post-conditions (right token at the indexed position, right script address). This is a non-trivial refactor — measure before/after with the I-01 benches first.

**Expected Benefit:**

CPU steps: dominant scans drop from O(N) to O(1) per lookup. Mem: small reduction (no intermediate Option allocations). Script size: slight increase (extra redeemer fields). **Magnitude needs benchmark** (see Risk).

**Risk:** medium — refactor touches every spend handler. **No baseline; benchmark before/after required.** The I-01 bench checklist must be in place before this optimization can be quantified. Adding indexed access also adds the risk of off-by-one errors that a future maintainer could introduce.

**Tests To Add:**

- Benchmark
  - [ ] Bench `encryption.spend.UseEncryption` before/after with the same realistic Transaction fixture (5 inputs, 2 ref inputs, 3 outputs)
  - [ ] Bench at high-N (10 inputs, 5 ref inputs) to characterise the asymptotic improvement
- Negative
  - [ ] `test fail__UseEncryption_rejects_wrong_own_input_idx`
  - [ ] `test fail__UseEncryption_rejects_wrong_bid_input_idx`
  - [ ] `test fail__UseEncryption_rejects_wrong_output_idx`

**Additional Notes:**

Considered a "should fix if/when transaction sizes grow" — the current protocol works fine at small N. The optimization is the canonical Aiken response to this pattern and is worth scheduling on the optimization backlog.

**Knowledge References:**

- [optimizations/aiken_optimization_guide.md](../../optimizations/aiken_optimization_guide.md) Pattern #12 (Avoid re-traversals), Pattern #20 (Don't compute, verify)
- [patterns/utxo_indexer.md](../../patterns/utxo_indexer.md)

N/A — code quality / size optimization.

Delete one. Update the caller. Standard practice: pick the better-named one (`add_commitments` reads more like the gnark semantic the comment describes; `sum_commitments_acc` is more generic). ## 15. Oracle Authentication & Freshness

**Not applicable.** The protocol consumes no external oracle data. The only "oracle-shaped" reference input is the genesis UTxO, which carries the `ReferenceDatum` and is authenticated by the one-shot genesis NFT `(genesis_pid, genesis_tkn)`. There is no time-sensitive oracle, so freshness against `validity_range` is also N/A.

The validity-range usage in the protocol is for time-locks, not oracle freshness:

- `encryption.UseSnark` bounds interval width to ≤1h and asserts `ttl ∈ [ub + 6h, 2*(ub + 6h)]`.
- `encryption.CancelEncryption` permissionless branch requires `lb > ttl`.
- `bidding.EntryBidMint` requires `locked_until >= ub + 6h`.
- `bidding.spend.RemoveBid` requires `lb > locked_until`.

Each use is appropriate for its semantic (upper bound for "earliest the action can affect future state"; lower bound for "earliest the action can occur").
